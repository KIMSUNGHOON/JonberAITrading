# NAV 손익 표시 설계 — 브로커 기준 기간 성과

**작성일**: 2026-07-31
**상태**: 구현 완료
**선행 아크**: `2026-07-31-cost-basis-single-source-design.md` (원가 단일화 — 배포 완료 `a8ea38b`)

## 문제

계좌 정보는 화면에 있으나 **실현손익·미실현손익과 기간 수익률을 보여주는 자리가 없다.**
포지션을 보면서 "이번 주 얼마 벌었나"를 알 방법이 없다.

## 이미 있는 것 — 새로 만들 것과 재사용할 것

설계 전 탐색에서 상당 부분이 이미 구현돼 있음이 드러났다.

| 자산 | 상태 | 이 아크에서 |
|---|---|---|
| `GET /api/trading/performance` | 있음. `start`/`end`/`base` 파라미터로 임의 기간, ka10074 실현손익 + kt00004 평가액 | **재사용** |
| `PerformancePanel.tsx` (542줄) | 있음. 실현손익·누적수익률·승률·일별 곡선 | 그대로 둔다 (Dashboard 타일) |
| `PositionsPanel.tsx` (386줄) | 있음. 이미 `/trading/operations`를 폴링 | **여기에 요약 스트립을 얹는다** |
| `daily_perf_snapshot` 테이블 | 있음. `equity` 일별 시계열 | **어떤 라우트로도 노출돼 있지 않다 — 유일한 신규 배선** |
| `pnlColor` 유틸, "조회 실패" 강등 패턴 | 있음 | 재사용 |

즉 이 아크의 실질은 **평가금 시계열을 API로 꺼내고, 이미 있는 조각들을 Positions 탭에서 한 화면에 모으는 것**이다.

## 실현손익 소스가 둘인 문제 — 규명 결과

같은 날짜에 두 값이 다르다. 07-22는 부호까지 반대였다(−115,714 vs +22,008).

| 소스 | 계산 주체 | 세금·수수료 |
|---|---|---|
| `daily_perf_snapshot.realized_pnl` | 브로커 ka10074 `rlzt_pl` | **세후** |
| `kr_realized_pnl.realized_amount` | 로컬이 체결로 계산 | **세전** |

07-22로 검산하면 정확히 맞는다: `22,008 − (107,100 + 30,614) = −115,706` vs 스냅샷 `−115,714` (차 8원).

나머지 날의 잔차는 **선행 아크가 고친 바로 그 오염** 때문이다. `kr_realized_pnl.entry_price`가
내부 평단을 쓰는데, 예컨대 317400 행의 `entry_price = 5,844.986…`은 브로커의 5,843이 아니라
**coordinator의 어긋난 평단 그 값**이다. 원가 단일화 아크는 앞으로의 실현손익 정확도까지 함께 올렸다.

`net_pnl == realized_pnl`은 **버그가 아니다.** `eod_snapshot.py:87-92`가 명시하듯 ka10074의
`rlzt_pl`은 이미 수수료·세금이 차감된 값이고, `commission`/`tax`는 참고용 내역이다. 다시 빼면 이중 차감이다.

## 원칙

**브로커가 손익의 단일 진실이다.** 원가에 적용한 원칙을 손익 표시에 그대로 잇는다.
`kr_realized_pnl`(로컬·세전)은 **표시에 쓰지 않는다.**

## 결정 사항

| 항목 | 결정 |
|---|---|
| 수익률 정의 | **평가금(equity) 변화 기준** — 미실현까지 포함한 실제 계좌 성과. 입·출금이 없는 계좌라 왜곡이 없다 |
| 기간 버킷 | **일 / 주 / 월 / 누적** — '년'은 제외. 11일치 데이터로 연간을 내면 허위다 |
| 기간 경계 | **캘린더 기준** — 주 = 이번 주 월요일부터, 월 = 이번 달 1일부터 |
| 데이터 공백 | **이월 처리** — 스냅샷이 없는 날은 직전 값을 잇는다. 공백 생성 원인(07-21 EOD 미실행)은 이 아크 범위 밖 |
| 위치 | **Positions 탭 상단 요약 스트립** (계좌 정보 옆) |
| 누적 분모 | 기존 `DEFAULT_BASE_ASSET_KRW = 500,000,000` 재사용 — 새로 정하면 기존 `PerformancePanel`과 숫자가 어긋난다 |

## 범위 A — `GET /api/trading/pnl-summary`

읽기 전용. never-raise. **섹션별 정직 강등** — 한 섹션이 실패해도 나머지는 정상 값을 반환하고,
실패한 섹션만 `null` + `errors` 사유를 채운다. 0이나 가짜 값으로 위장하지 않는다
(`/operations`·`/performance`가 이미 쓰는 패턴).

```
{
  "unrealized": { "total": 213306, "holdings": 1 } | null,
  "realized":   { "day": 984533, "week": 984533, "month": -2269563, "total": -2269563 } | null,
  "equity_return": {
    "day":   { "pct": 0.0139,  "basis": "prior_close" },
    "week":  { "pct": 0.4692,  "basis": "prior_close" },
    "month": { "pct": -0.4479, "basis": "base_asset" },
    "total": { "pct": -0.4479, "basis": "base_asset" }
  } | null,
  "as_of": "2026-07-31",
  "errors": {}
}
```

### 섹션별 소스

- **`unrealized`** — `/trading/operations?market=kiwoom`의 `holding[].pnl` 합. 브로커 산출, 세후.
  이미 판정된 표시용 SSOT다.
- **`realized`** — ka10074를 **한 번만** 호출한다. `start` = `min(이번 달 1일, 데이터 시작일)`,
  `end` = 오늘. 반환된 `daily` 시리즈(`dt`, `pnl`)를 버킷별로 합산한다.
  **버킷마다 호출하면 안 된다** — Kiwoom은 초당 약 1.4요청으로 제한된다.
  여기서 **데이터 시작일 = `daily_perf_snapshot`의 가장 이른 `trade_date`** (현재 2026-07-16).
  스냅샷이 0행이면 이번 달 1일을 쓴다.

  주의: 위 예시의 `month`/`total` = −2,269,563은 **스냅샷 행을 합산한 참고치**다.
  실제 구현은 ka10074를 직접 호출하므로 **스냅샷이 빠진 07-21(−38,520 상당)을 포함해
  다른 값이 나올 수 있고, 그쪽이 옳다.** 스냅샷 합산을 정답으로 삼아 검증하지 마라.
- **`equity_return`** — `storage.get_daily_perf_snapshots()`의 `(trade_date, equity)` 시계열.

### 평가금 수익률 산식

버킷 `[start, end]`에 대해:

```
end_equity   = trade_date <= end 인 마지막 행의 equity
start_equity = trade_date <  start 인 마지막 행의 equity   # 기간 시작 직전 종가
               (그런 행이 없으면 DEFAULT_BASE_ASSET_KRW, basis="base_asset")
pct = (end_equity / start_equity - 1) * 100
```

`basis` 필드로 분모가 무엇이었는지 드러낸다 — 계좌 개시 이전으로 거슬러 갈 수 없는 버킷
(현 데이터에서 월간·누적)은 기준자산 대비임을 화면에서 밝혀야 한다.

**2026-07-31 실측으로 재현되는 값** (구현 검증에 그대로 쓴다):

| 버킷 | start_equity | end_equity | pct | basis |
|---|---|---|---|---|
| 일 | 497,691,136 (07-30) | 497,760,401 | **+0.0139%** | prior_close |
| 주 (월요일 07-27 시작) | 495,435,889 (07-24) | 497,760,401 | **+0.4692%** | prior_close |
| 월 (07-01 시작) | 500,000,000 | 497,760,401 | **−0.4479%** | base_asset |
| 누적 | 500,000,000 | 497,760,401 | **−0.4479%** | base_asset |

주간이 07-24 종가를 기준으로 삼는 것이 이월 규칙의 핵심이다 — 07-25·07-26은 주말이라 행이 없고,
07-27(월) 행은 그날 **장 마감 후** 값이라 시작점으로 쓰면 그 주 월요일의 성과가 통째로 빠진다.

**구현 중 확정된 차이 — `unrealized`는 엔드포인트에 없다.** 응답 예시에는 있었으나,
같은 스펙 본문이 "`PositionsPanel`은 이미 `/operations`를 폴링하므로 미실현손익은
추가 조회 없이 나온다"고 명시한다. 엔드포인트가 이를 직접 반환하려면 같은 브로커
보유 조회를 30초마다 한 번 더 해야 하고, 이는 Kiwoom 레이트리밋(초당 약 1.4요청)
제약과 부딪힌다. 미실현손익은 `PositionsPanel`이 가진 행에서 합산해
`PnlSummaryStrip`에 prop으로 내려준다.

## 범위 B — Positions 탭 요약 스트립

`PositionsPanel.tsx` 상단, 기존 보유 테이블 **위**에 요약 스트립을 얹는다.
`PositionsPanel`은 이미 `/operations`를 10초 주기로 폴링하므로 **미실현손익은 추가 조회 없이** 나온다.
`pnl-summary`는 별도 폴링(30초, `PerformancePanel`과 동일 주기)으로 붙인다.

표시 요소:

- **미실현손익** — 금액 + 보유 종목 수
- **일 / 주 / 월 / 누적** 각각 평가금 수익률(%)과 실현손익(원)을 한 열에 세로로 쌓는다
- 부호 색상은 기존 `pnlColor` 유틸을 그대로 쓴다 (신규 색 규칙 금지)
- `basis == "base_asset"`인 버킷은 분모가 기준자산임을 드러낸다 — 툴팁이 아니라 화면에 보이는 표기로
- 섹션 실패 시 그 섹션만 **"조회 실패"** (기존 강등 패턴). 다른 섹션은 계속 값을 보여준다
- 데이터가 없는 버킷(예: 개시 첫날의 주간)은 `—`

## 검증

| 대상 | 검증 |
|---|---|
| 일간 산식 | 07-30 종가 497,691,136 → 07-31 497,760,401 = +0.0139% |
| 주간 이월 | 주 시작 07-27(월)인데 기준은 07-24 종가 495,435,889 = +0.4692% (07-27 행이 아님) |
| 월간 base_asset 대체 | 07-01 이전 행이 없으므로 500,000,000 기준, `basis="base_asset"` |
| 공백 이월 | 07-21 행이 없어도 07-20 → 07-22 구간이 끊기지 않는다 |
| 실현손익 버킷 | ka10074 `daily`를 **1회** 호출해 일/주/월/누적을 만든다 (호출 4회면 실패) |
| 미실현 SSOT | `/operations` `holding[].pnl` 합 — `kr_realized_pnl`을 쓰지 않는다 |
| 섹션 강등 | ka10074만 실패시켜도 `equity_return`·`unrealized`는 정상 값이 나온다 |
| never-raise | 스냅샷 0행, 브로커 전면 실패에서도 500이 아니라 `errors` 채운 200 |

## 명시적 제외

**`daily_perf_snapshot` 공백 보완** — 07-21은 거래일이고 실현손익 −38,520이 있었는데 EOD가 돌지
않아 행이 없다. 원인 규명과 백필은 별도 아크. 이 아크는 이월로 흡수한다.

**`kr_realized_pnl`의 오염된 `entry_price`** — 과거 행은 어긋난 내부 평단으로 기록돼 있다.
표시에 쓰지 않으므로 이 아크에서는 무해하다. 소급 정정은 별도 판단.

**'년' 버킷** — 데이터가 07-16부터라 11일치다. 쌓이면 그때 추가한다.

**기준자산 500,000,000의 하드코딩** — `eod_snapshot.py:31`이 이미 "persisted base-asset setting이
아직 없다"고 기록해 둔 기존 부채다. 새 상수를 만들지 말고 기존 값을 재사용한다.

**계좌 스냅샷 동결** (`stock_value`가 하루 종일 얼어붙는 문제) — 선행 아크 스펙이 이미 별도 아크로
분리했다. 이 아크는 `/operations`를 쓰므로 영향받지 않는다.
