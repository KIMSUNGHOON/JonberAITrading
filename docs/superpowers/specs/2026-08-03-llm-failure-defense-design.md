# LLM 장애 방어·관측 설계 — 장애를 의견으로 세탁하지 않는다

**작성일**: 2026-08-03
**상태**: 구현 완료
**계기**: 2026-08-03 12:50~13:14 라이브 장애 — Agent Group Chat이 LLM 없이 토론을 "완료"했고, 운영자는 폰으로 아무 통지도 받지 못했다.

## 무슨 일이 있었나

12:50부터 LLM 백엔드가 전멸했다. 사용자가 Claude 사용량 한도를 지목했고, 조사 결과 시스템은 **그것이 한도였는지조차 기록하지 못했다.**

```
error="all backends failed for task 'general': claude exited 1: "
error="no available backend for task 'general'"     ← 토론 진행자
```

콜론 뒤가 비어 있다. 그 공백이 이 설계의 출발점이다.

### 실패의 사슬 — 하나에서 시작해 일곱으로 번졌다

```
① claude_cli.py:77이 stderr만 읽는다 (CLI는 stdout에 사유를 쓴다)
   → "usage limit" 문자열이 _classify()에 도달하지 못한다
   → _RATE_MARKERS에 "usage limit"이 이미 있는데도 매칭 실패
   → BackendTransientError가 아닌 일반 BackendError로 오분류
   → 서킷이 rate-limit용 2배 쿨다운을 받지 못한다
   → base_agent.py:120이 에러 문자열을 "분석 결과"로 반환한다
   → 투표 파서가 표를 못 찾고 합의 불성립 → 가짜 NO_ACTION으로 "완료"
   → 통지 경로가 없어 아무도 모른다
```

### 실증

`--output-format json`인 Claude CLI는 **실패해도 stdout에 JSON으로 사유를 쓰고 stderr는 비운다.** 잘못된 모델로 재현했다:

```
rc=1
stdout: {"is_error":true, "result":"There's an issue with the selected model..."}
stderr: (비어 있음)                    ← 코드가 읽는 유일한 소스
```

`claude_cli.py:25`의 `_RATE_MARKERS = ("rate limit", "overloaded", "429", "usage limit")`.
**시스템은 한도를 인식할 준비가 되어 있었다. 배선 한 곳이 끊겨 있었을 뿐이다.**

### 헬스체크가 거짓말을 했다

`/api/llm/stats`가 장애 중에 답한 내용:

| 백엔드 | 보고 | 실제 |
|---|---|---|
| `openrouter` | unavailable | 401 (09:00:24부터, 통지 없음) |
| `codex_cli` | healthy: false | 사용 불가 |
| `claude_cli` | **healthy: true** | **전 호출 실패 중** |

`health()`는 `--model haiku`로 프로브하는데(`claude_cli.py:96-97`) 실제 호출은 설정 모델을 쓴다. **모델·플랜 단위 한도는 haiku 프로브를 통과한다.**

### 피해와 비피해

12:50:09의 토론은 `moderator_making_decision` → `moderator_decision_made`가 **0.2ms** 만에 끝났다. LLM 호출이 없었다는 뜻이다. 결과는 `NO_ACTION`과 `HOLD`(손절 미하향)로 **안전한 쪽이었고 주문은 나가지 않았다.** 당일 체결 2건(316140)은 09:30·10:11로 장애 이전이다.

**해가 없었던 것은 설계가 막아서가 아니라 기본값이 우연히 보수적이었기 때문이다.**

## 원칙

**장애를 의견으로 세탁하지 않는다.** 실패가 정상 경로로 흘러들면 원장에 가짜 결정이 쌓이고, 화면에서 "합의 보류"와 "판단 불가"가 구분되지 않는다.

**탐지가 정책보다 먼저다.** 지금은 한도 메시지가 실제로 어떻게 생겼는지조차 모른다.

이 원칙은 이번 아크가 대기를 구현하는 것과 모순되지 않는다. 대기 상한 5분은 **신선도에서
유도된 값**이라 한도 메시지의 내용과 무관하게 정할 수 있다. 반면 리셋 시각을 읽어 그 시점까지
정확히 기다리는 것은 메시지 형식을 알아야 하므로 **이번 범위에서 제외**한다(아래 명시적 제외).
즉 이번 아크는 "얼마나 기다릴 수 있는가"(신선도)로 대기를 정의하고, "언제 풀리는가"(메시지)는
포착이 쌓인 뒤에 다룬다.

## 대기의 정체 — 신선도가 허용하는 만큼

사용자 요구는 "usage limit이 reset될 때까지 대기"다. 그러나 무한 대기는 안 된다.

**멈췄던 토론은 멈춘 시점의 가격·차트를 들고 있다.** 12:50에 멈춘 토론이 15:00에 재개되면 2시간 전 데이터로 매매를 결정한다. 그것은 지금의 가짜 `NO_ACTION`보다 위험하다 — 아무것도 안 하는 쪽에서 **잘못된 것을 하는 쪽**으로 바뀌기 때문이다.

그래서 대기 상한은 **5분**이다(감시 주기 1분의 5배).

| 상황 | 동작 |
|---|---|
| 한도가 5분 안에 풀림 | 라우터가 기다렸다 이어간다 — 토론은 자기 컨텍스트가 유효한 채 살아남는다 |
| 5분을 넘김 | 던진다 → 토론은 정직하게 실패 → **다음 감시 주기(1분)에 새 데이터로 재시작** |
| 긴 장애 (서킷 개방) | 대기 없이 즉시 실패 → 통지 → 주기마다 재시도 |

버리는 것이 손해로 보이지만 아니다. 재개해서 아끼는 것은 "이미 한 분석"뿐이고, 잃는 것은 **판단의 근거**다. 감시 주기가 1분이라 한도가 풀리면 곧 새 토론이 신선한 데이터로 시작한다.

**리셋 시각을 모를 때**: 메시지에 시각이 없거나 파싱이 실패하면 5분 상한을 그대로 쓴다. 파싱 성공은 최적화일 뿐이며, 없어도 동작이 정의된다.

## 범위

### A. 사유 포착 — 이 아크의 토대

`agents/llm/backends/claude_cli.py:77`과 `agents/llm/backends/codex_cli.py:83`이
분류 입력에 **stdout을 포함**한다. 현재는 `err`(stderr)만 넘긴다.

그 위에 **한도 판정 루틴**을 얹는다 — 실패를 받아 "이것이 사용량 한도인가, 메시지 원문은
무엇인가"를 판정해 구조화된 형태로 남긴다. 대응 정책이 아니라 **판정과 기록**까지가 A의 범위다.

A만으로 연쇄가 풀린다: `"usage limit"`이 `_RATE_MARKERS`에 걸려 `BackendTransientError`로
올바르게 분류되고, 서킷이 2배 쿨다운을 받는다.

### B. 헬스체크 대표성

`claude_cli.py`의 `health()` 프로브를 `--model haiku` 하드코딩에서 **그 백엔드 인스턴스가
실제로 쓰는 모델**(`self.model`, `__init__`의 `model` 인자로 주입됨)로 바꾼다.
프로브 비용이 오르지만, 대표성 없는 헬스 신호는 그보다 비싸다 — 오늘 `healthy: true`가
전 호출 실패를 가렸다.

`codex_cli.py`의 `health()`도 같은 문제가 있는지 확인하고 같은 원칙을 적용한다.

### C. 라우터의 한도 대기

`agents/llm/router.py`가 체인 소진 시 `LLMAllBackendsFailed`를 던지는 두 자리
(`:193` 가용 백엔드 없음, `:218` 전 백엔드 실패)에서, 실패 원인이 사용량 한도이면
**최대 5분까지** 재시도하며 기다린 뒤 던진다.

**한도 외 실패는 기다리지 않는다.** 인증 오류·모델 부재·네트워크 실패 등은 기다린다고
풀리지 않으므로 지금처럼 즉시 던진다. 대기는 "기다리면 풀리는 종류"에만 적용된다.

**대기를 라우터에 두는 이유**: 토론·감성분석·스캐너가 모두 라우터를 거치므로 한 곳만
고치면 전부 혜택을 본다. `chat_room.start()`는 분석→토론→투표→결정을 한 코루틴에서
통째로 돌기 때문에, 라우터가 기다리면 토론은 자기 지역 상태를 보존한 채 자연히 함께
기다린다. **`SessionStatus`에 새 상태를 넣을 필요가 없다.**

서킷이 이미 열려 있으면 체인이 비어 즉시 실패한다 — 긴 장애에 5분씩 낭비하지 않는다.

### D. 정직한 실패

`services/agent_chat/agents/base_agent.py:120`이 LLM 실패 시
`return f"분석 중 오류 발생: {str(e)}"`로 **에러 문자열을 분석 결과처럼 반환**하는 것을
멈추고 실패를 전파한다. 토론은 실패로 끝나고 원장에 가짜 결정이 남지 않는다.

### E. Telegram 통지

`services/telegram/service.py:667`의 `send_system_status()`가 이미 있다. 여기에 배선한다.

통지 대상:
- 라우터에 가용 백엔드가 없어졌을 때 (오늘 아침 OpenRouter 401이 이 경우다)
- 토론이 LLM 장애로 실패했을 때

**원인별 1회 래치**를 건다 — 원가 드리프트 통지와 같은 형태로, 감시 주기(1분)마다 반복
발송되지 않게 한다. 원인이 해소되면 래치를 풀어 재발 시 다시 알린다.

## 검증

| 대상 | 검증 |
|---|---|
| A 사유 포착 | rc≠0이고 stderr가 비어 있어도 stdout의 `result`가 에러 메시지에 담긴다 |
| A 한도 분류 | stdout에 "usage limit"이 있으면 `BackendTransientError`로 분류된다 |
| A 서킷 | 한도 분류 시 쿨다운이 2배로 적용된다 |
| B 헬스 | 실제 사용 모델로 프로브한다 — haiku 하드코딩이 남아 있지 않다 |
| C 대기 상한 | 한도 지속이 5분을 넘으면 던진다. 5분 이내면 성공 후 이어간다 |
| C 서킷 개방 시 | 대기 없이 즉시 실패한다 |
| C 리셋 시각 미상 | 파싱 실패해도 5분 상한으로 동작이 정의된다 |
| D 세탁 제거 | LLM 실패 시 `"분석 중 오류 발생"` 문자열이 의견으로 흘러들지 않는다 |
| D 원장 | LLM 전멸 상황에서 `NO_ACTION` 결정이 기록되지 않는다 |
| E 통지 | 가용 백엔드 소진 시 1회 발송, 반복 주기에 재발송 없음, 해소 후 재발 시 다시 발송 |

## 명시적 제외

**OpenRouter 401 키 갱신** — 코드가 아니라 사용자 조치 영역이다. 다만 E의 통지 대상에는
들어간다. 오늘 아침 09:00:24부터 죽어 있었는데 아무도 몰랐던 것이 이 아크의 출발점이다.

**`chat_room` 상태 기계** — 대기를 라우터가 맡으므로 손대지 않는다. `SessionStatus`에
새 상태를 추가하지 않는다.

**리셋 시각 파싱의 정교화** — 실제 한도 메시지를 포착(A)한 뒤에 별도로 판단한다. 이번
아크는 파싱 실패해도 5분 상한으로 동작이 정의되게만 한다.

**`codex_cli` 불건강 원인** — 오늘 `healthy: false`였으나 원인 조사는 이 아크 범위 밖이다.
B가 헬스 신호를 정직하게 만들면 그 자체가 다음 조사의 입력이 된다.

### 구현이 설계를 넘어선 지점

**B 헬스: 정적 프로브 캐시 → 실제 호출 트래픽 기반 관측**(커밋 `930539f`). 설계는
`--model haiku` 하드코딩을 실제 사용 모델로 바꾸는 것까지만 다뤘다. 구현은 한 걸음
더 나갔다 — 부팅 시 1회 프로브해 캐시한 값을 그대로 보고하던 구조 자체가 문제였다
(오늘 장애 내내 `healthy: true`가 박제된 이유). `resolve()`의 헬스 게이트를 제거하고
(실패로 죽음 표시된 백엔드가 후보에서 빠지면 다시 호출될 일이 없어 영구 배제
데드락이 된다), 매 실제 호출의 성패로 헬스 표시를 갱신하도록 바꿨다. 회복 판정은
서킷 브레이커의 쿨다운이 전담하고, 헬스 캐시는 `/api/llm/stats`용 관측 표시로만
남는다. `startup()`도 claude 인스턴스 하나(sonnet)가 아니라 둘(opus·sonnet)을 모두
프로브하도록 넓혔다 — 전략용 opus 인스턴스의 한도가 관측 대상 밖에 있었다.
