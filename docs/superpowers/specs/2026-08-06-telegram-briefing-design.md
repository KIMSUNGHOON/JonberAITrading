# Telegram 브리핑·조회 명령 확장 — 설계

- 날짜: 2026-08-06
- 범위: **조회 전용.** 매매 로직 변경 0. 상태를 바꾸는 명령은 추가하지 않는다.
- 목표: 2026-08-07 개장(09:00) 전 배포

## 1. 문제

폰에서 볼 수 있는 것이 7개 명령(`/status` `/positions` `/pending` `/report`
`/halt` `/auto` `/help`)뿐이라, 오늘 실제로 필요했던 질문들에 답이 없었다.

- **"왜 안 샀나"** — 이번 세션 전체가 사실상 이 질문이었다. 316140이 ADD를
  7회 의결하고 체결 0건인 이유를 찾는 데 DB 조회 + 로그 grep + 코드 추적 +
  오프라인 재현까지 필요했다.
- **"자리가 없어 놓친 게 얼마나 되나"** — 오늘 만장일치 BUY 두 종목이 15회
  거절됐는데 폰에서는 알 방법이 없었다.
- **"지금 얼마나 실려 있나"** — 계좌의 90%가 예수금인 상태가 몇 주 이어졌는데
  비중을 한눈에 보는 화면이 없었다.

## 2. 만드는 것

명령 4개. 전부 조회 전용이고, 오늘 이미 작성한 SQL을 재사용한다.

| 명령 | 답하는 질문 |
|---|---|
| `/brief` | 오늘 뭘 알고 시작해야 하나 (자산 배분·보유·어제·오늘 준비) |
| `/why <종목>` | 왜 샀나 / 왜 안 샀나 |
| `/slots` | 자리가 없어 놓친 게 얼마나 되나 |
| `/exposure` | 목표 노출도가 얼마고 무엇이 묶고 있나 |

추가로 `/brief`를 **평일 08:30에 자동 발송**한다(KRX 영업일만).

### 뺀 것

- `/reeval` — 49분 관측이 성공으로 끝나 질문이 닫혔다. `/brief` 한 줄로 충분.
- `/trades` — 3일 연속 체결 0건이고 `/report`가 EOD를 덮는다.
- **리스크 파라미터 변경 명령** — 폰에서 라이브 게이트를 바꾸는 오조작 비용이
  크다. `GATE_PROTECTED_FIELDS`가 LLM 드리프트를 막으려 존재하는데 폰 명령으로
  뒷문을 내는 셈이 된다. **조회는 폰, 변경은 API.**

## 3. 구조

| 파일 | 책임 |
|---|---|
| `services/telegram/briefing.py` (신규) | 수집기 + **순수 포맷터** |
| `services/telegram/commands.py` (수정) | 핸들러 4개 + `register_command` |
| `app/main.py` (수정) | 08:30 스케줄 잡 |

포맷터는 **데이터 dict를 받아 문자열을 돌려주는 순수 함수**다. DB도 API도
모른다 — 테스트 대부분이 여기서 끝난다. 수집기가 I/O를 전담한다.

기존 헬퍼를 그대로 쓴다: `_safe()`(소스별 독립 저하), `source_status()`(빈값 /
조회 실패 / 미설정 구별), `_truncate()`(3,900자), `_reply()`.

## 4. 실패 처리

**소스 하나가 죽어도 나머지는 나간다.** `_safe()`로 각 조회를 감싸고, 실패한
섹션만 `조회 실패`로 표시한다. 이는 기존 명령들이 이미 쓰는 규약이다.

**조용히 0을 찍지 않는다.** 오늘 관측 유닛에서 세운 규칙과 같다 — 0으로 채운
줄은 진짜 0과 구별되지 않는다.

**엣지 케이스**: 08:30에는 `exposure_shadow`에 **오늘 행이 없다**(장중에만
쌓인다). 목표 노출도는 "최근 1행 + 그 시각"을 보여주고, 아예 없으면
`관측 시작 전`으로 표시한다. **어제 값을 오늘 값인 척 보여주지 않는다.**

**3,900자 상한**: 보유 5종 + 슬롯 거절 3종 기준으로 여유가 크다. 슬롯 거절이
많은 날을 대비해 `/slots`는 상위 10종까지만 표시하고 나머지는 건수만 적는다 —
`_truncate`가 잘라 조용히 사라지는 것보다 낫다.

## 5. 자동 발송

`app/main.py`의 기존 스케줄러 패턴(`holiday_update_scheduler`)을 따른다.
`AsyncIOScheduler` + cron(월~금 08:30 KST). 발송 직전 `krx_holiday` 서비스로
**당일이 영업일인지 확인**하고 아니면 건너뛴다(휴장일 25일치가 이미 로드돼 있다).

발송 실패는 삼킨다 — 브리핑이 못 나가는 것이 앱을 죽이면 안 된다.

## 6. 테스트

**포맷터(대부분)** — 각 섹션 렌더링 / 소스 실패 시 그 줄만 저하되는지 /
비중 합이 100%인지 / `exposure_shadow` 부재 시 `관측 시작 전` 표기 /
`/slots` 10종 초과 시 잘림 표기 / 3,900자 이내.

**수집기** — 소스별 예외가 전파되지 않는지. `isolated_storage_service` 필수.

**스케줄러** — 잡 등록, 휴장일 스킵, 발송 실패 비전파.

**회귀 가드** — 기존 7개 명령의 등록과 동작이 그대로인지.

## 7. 성공 판정 (배포 후)

폰에서 네 명령이 응답하면 성공이다. 08:30 자동 발송은 **2026-08-07 아침에
실제로 도착하는지**로 판정한다 — 도착하지 않으면 스케줄 등록 실패이지
"발송할 것이 없었던" 것이 아니다.
