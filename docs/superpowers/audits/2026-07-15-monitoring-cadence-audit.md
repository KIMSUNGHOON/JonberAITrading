# 감시 주기 vs Kiwoom 레이트 한도 실사 (2026-07-15)

> 2-에이전트 READ-ONLY 실사 + 종합. 설계 제안.

두 실사자의 조사가 서로 충돌하는 두 지점을 코드로 직접 확인해 확정한 뒤 종합했다. 결론부터: **P3 재평가는 실제로 구현되어 있고**(실사자1 정확, 실사자2의 "미구현" 오판 — `position_manager.py:255-283`, 오늘 커밋된 코드), **agent-chat 5분 체크는 Kiwoom을 전혀 안 부르지만**(실사자2 정확) 그 대신 **관심종목 가격이 주기적으로 갱신되지 않아**(start/승인 시에만 리프레시 — `coordinator.py:194,429`가 유일 호출처) 5분을 줄여도 반응성이 안 오른다. 이 두 사실이 권고를 바꾼다.

## A. 레이트 예산과 현재 사용량

**실제 천장 = 1 request / 0.7s ≈ 1.4286 req/s (≈ 85.7 req/min).** 버킷 단위이며 QUERY(시세·호가·미체결·체결·계좌·종목리스트 전부)와 ORDER(주문 `kt10*`)는 독립 버킷이다. 조회 루프는 전부 **QUERY 버킷 하나**를 공유한다(프로세스 전역 싱글턴, `kiwoom_singleton.py`).

- 근거: `rate_limiter.py:40`의 `min_interval=0.7`이 토큰 잔량 체크보다 **먼저** 적용된다(`acquire()` :64-88). 그래서 명목 "5토큰/5refill"(≈초당 5건, 코드 주석이 인용한 약관 제11조 값 — **저장소 어느 공식 문서에도 정량 수치 없음, 검증 불가**)은 죽은 설정이고, 실효 상한은 1.43 req/s로 자체 하드캡되어 있다.
- 서버측 실제 한도는 사후 에러코드로만 존재: `1700 허용된 요청 개수 초과`, `1687 재귀 호출 제한`. 정량치·스코프(IP당/앱키당)는 문서에 없음.

**현재 지속 사용량**(라이브 실측, 보유 N=2 · 워치 W=4 · 큐/추적미체결 0):

| 상태 | 지속 req/s | 천장 대비 |
|---|---|---|
| 백엔드만 (FE 미오픈) | **≈ 0.68** | 48% |
| + FE 대시보드 상시 오픈 | **≈ 1.13–1.17** | ~80% |

**헤드룸: FE 오픈 시 ≈ 0.26–0.30 req/s(~18–20%)로 매우 빠듯.** 백엔드만이면 ≈ 0.75 req/s(~52%) 여유. **핵심: 지금 예산을 갉아먹는 주범은 감시 루프가 아니라 FE 폴링(특히 OperationsPanel 5초의 pending+filled ≈ 0.4 req/s)이다.** RiskMonitor 자체는 N/3 = 0.67 req/s에 불과.

설계 기준선으로 삼을 값: **지속 부하 ≤ 1.0 req/s(천장의 70%)를 목표, ≤ 1.2 req/s(85%)를 절대 상한**으로 둔다. 이유는 D에서.

## B. 두 종류 주기 — 여기가 핵심

사용자의 "주기를 타이트하게"는 **두 종류를 섞어서 말하고 있고, 둘의 병목이 완전히 다르다.**

### B-1. 가격 감시 주기 = **API-bound** (사용자가 맞다 — 더 빨라져도 된다, 단 조건부)

- **보유종목**: RiskMonitor 1초 루프가 이미 돈다. 그러나 실효 반응지연을 결정하는 건 루프(1초)가 **아니라 `stock_info` 캐시 TTL(3초)**이다 — 1초마다 돌아도 캐시 때문에 종목당 실호출은 3초에 1번, 비용 = **N/3 req/s**. 즉 손절 감지는 이미 ~3초 내로 충분히 빠르다. **더 빠르게 하려면 루프가 아니라 캐시 TTL을 낮춰야 하고, 비용은 N에 비례**해 커진다.
- **관심종목(엔트리 후보)**: 여기가 **진짜 반응성 구멍**이다. RiskMonitor는 보유종목만 본다. 워치 가격(`w.current_price`)은 start()·승인 시에만 갱신되고 **주기 루프가 없다.** 그래서 5분 `_check_watch_list`가 target_entry와 비교하는 값은 **장중 내내 얼어있는 가격**이다 → **5분을 1분으로 줄여도 같은 헌 숫자를 더 자주 비교할 뿐, 반응성 0.** 이걸 고치려면 워치용 주기 리프레시 루프를 새로 넣어야 하고 그건 **W/interval req/s의 실제 Kiwoom 비용**을 발생시킨다.

→ **API-bound 쪽은 사용자가 옳다.** 단, "루프를 빠르게"가 아니라 **"캐시 TTL을 N·W에 맞게 동적으로"** 가 정확한 레버다.

### B-2. LLM 재평가/토론 주기 = **LLM·churn-bound** (사용자가 무조건 옳지는 않다)

- **P3 재평가(60분/3%)와 agent-chat 5분 체크는 Kiwoom을 추가로 부르지 않는다.** P3는 같은 30초 사이클이 이미 받아온 캐시 가격으로 "토론 트리거할지"만 판단하는 순수 의사결정 스로틀이다. 즉 **여기서 "타이트하게"의 비용은 Kiwoom 예산이 아니라 LLM 호출비 + 결정 churn**이다.
- **주의점**: 주기적 재평가 간격을 60분→5분으로 내리면 각 포지션 논지를 시간당 12배 재심의 → **매 틱 새 결정으로 흔들림(flip-flop), LLM 비용 폭증, `max_discussions_per_position=5`(생애 누적 상한)를 2시간 안에 소진해 그 뒤엔 완전 침묵.** 이건 "빠른 반응"이 아니라 오히려 **더 나쁜** 결과다.
- **사용자가 맞는 부분**: 시장이 빨리 움직일 때 빨리 재판단해야 한다 — 맞다. **정답 레버는 "주기 단축"이 아니라 이미 존재하는 가격변동 트리거(3%)를 낮추는 것.** P3는 `60분 경과 OR 3% 이동` 두 트리거를 갖고 있고, 후자가 바로 "빠른 시장" 대응 장치다. 주기는 백스톱으로 길게 두고 **변동 임계치를 낮추면 churn 없이 반응성만 올라간다.**

### 루프별 현재→권고

| 루프 | 현재 | 권고 | 근거 |
|---|---|---|---|
| **RiskMonitor 루프** | 1s | **1s 유지** | 캐시가 흡수. 루프는 병목 아님. 건드리지 말 것. |
| **`stock_info` 캐시 TTL (보유 반응성 실레버)** | 3s 고정 | **동적** `TTL_held = clamp(⌈N/0.8⌉, 2s, 20s)` | N≤2면 **2s로 오히려 단축**(반응↑), N↑ 시 자동 후퇴. N=5면 7s여야 천장 안 넘음. |
| **워치 가격 리프레시** | 없음(얼어있음) | **신규 루프**, `TTL_watch = clamp(⌈W/0.3⌉, 10s, 60s)` | W=4 → ~15s. **이게 워치 반응성의 진짜 해법.** 비용 ~0.29 req/s. |
| **agent-chat `_check_watch_list`** | 5min | **60s** | 이 체크는 API 비용 0(저장가격만 읽음). 실제 상한은 `min_discussion_interval 30min` + `max_concurrent 3`이 잡음 → 자주 돌려도 안전. 단 **위 워치 리프레시 루프가 선행돼야 의미 있음.** |
| **PositionManager 루프** | 30s | **30s 유지** | RiskMonitor가 캐시를 데워둬 사실상 공짜. 반응 게이트 아님. |
| **P3 `reeval_interval_minutes`** | 60 | **30** | 시간당 2회 백스톱이면 충분. 짧게 갈수록 churn·비용만. |
| **P3 `reeval_price_change_pct`** | 3.0 | **2.0** | **여기가 "빠른 시장" 정답 레버.** 신선한 캐시가로 2% 이동 시 수초 내 재평가 트리거, churn 없음. |
| **P3 `min_discussion_interval_minutes`** | 30 | **15** | 변동성 포지션이 30분 침묵당하지 않게. 여전히 스팸 방지. |
| **P3 `max_discussions_per_position`** | 5(생애 누적) | **8, 또는 "일/세션 롤링"으로 의미 변경** | 현재는 5회 후 영구 침묵 — 종일 보유 포지션엔 결함. 짧은 간격과 함께 반드시 완화. |

### 동적 주기 공식 (하드코딩 금지)

보유 N + 워치 W 티커를 예산 `B_price ≈ 0.9 req/s`로 신선 유지:
```
TTL_held(N)  = clamp(⌈N / 0.8⌉, 2, 20)  초
TTL_watch(W) = clamp(⌈W / 0.3⌉, 10, 60) 초
```
- N=2,W=4: 보유 2s(0.67 req/s) + 워치 15s(0.27) + reconcile 0.017 ≈ **0.96 req/s (67%)** — 안전.
- N=5,W=6: 보유 7s(0.71) + 워치 20s(0.30) ≈ **1.01 req/s** — 여전히 안전. **고정 3s였으면 보유만 1.67로 천장 초과.**

### FE 폴링 최적화 (헤드룸의 진짜 원천)

- **OperationsPanel 5s → 10s** + pending/filled 캐시 TTL 5s→10s: **0.4 → 0.2 req/s** (−0.2, 위 워치 루프 비용을 정확히 상쇄).
- **탭 가시성 게이팅**: `document.visibilityState`로 비포커스 시 폴링 정지. 백엔드 baseline이 0.68뿐이므로 대시보드 안 볼 때 예산 전량이 감시 루프로 반환됨. 가장 큰 단일 이득.
- Scratchpad 30s 배치: 자체 TTL을 30s로 맞춰 3s 캐시 무의미 재조회 제거(마이너).

## D. 리스크

1. **"초과"는 429가 아니라 손절 지연으로 나타난다.** 내부 리미터는 초과 시 에러 대신 `acquire()`가 **최대 30초까지 큐잉 대기**시킨다. 그러면 같은 버킷을 기다리는 RiskMonitor 1초 틱이 굶어 **손절 감지가 수초~수십초 지연**된다. 그래서 헤드룸은 선택이 아니라 **실시간 안전성의 조건** — 설계 부하를 70%로 묶는 이유다.
2. **mock vs live 함정.** mock 서버(`KIWOOM_IS_MOCK`)는 실제 레이트 강제가 없어 아무리 조여도 "잘 된다". 절대 mock 동작 기준으로 튜닝하지 말 것 — **내부 리미터(1.43 천장) 기준으로만** 튜닝. live에서만 터진다.
3. **live 앱키 한도는 문서화된 정량치가 없다.** 저장소엔 `1700/1687` 반응형 코드뿐. 스코프(IP당/앱키당)도 불명. 내부 1.43 천장은 명목 ~5건/s(미검증)의 28%로 **자체 보수 설정**이라 이론상 올릴 여지는 있으나, **live 검증 전엔 min_interval을 낮추지 말 것** — 반복 1700은 앱키 스로틀/차단 위험. (`client.py:161-232` 지수백오프가 재시도는 처리.)
4. **동적 주기는 필수, 고정값은 전부 틀림.** N=2에 안전한 3s는 N=5에서 천장 붕괴, N=10에 안전한 15s는 N=2에서 불필요하게 느림. 단일 하드코딩 숫자는 존재할 수 없다 → C의 `TTL(N,W)` 공식으로 스케일.
5. **선행 정리 2건 (조이기 전에 고쳐야 함):**
   - **`coordinator.py:101 KiwoomRateLimiter(redis_client)` 버그** (실사자1): redis_client를 query_limit 위치인자로 꽂는 실수. 이 경로(services/trading OrderAgent)가 기동되면 `float(None)` TypeError거나, 최악의 경우 **전역 버킷을 공유하지 않는 별도 리미터**가 생겨 실제 발사율이 2배가 된다. 조이기는 "버킷 하나 공유"를 전제하므로 이걸 먼저 확정.
   - **`pending_alerts_count=1542` 이상** (실사자2): RiskMonitor가 USER_APPROVAL 모드에서 dedup 없이 매 틱 alert 적재. 감시 주기를 조이면 **더 빠르게 쌓인다.** 반응성 튜닝과 별개로 dedup 선행 필요.
6. **스캐너 동시 가동 = 구조적 병목.** 백그라운드 스캐너는 같은 전역 QUERY 버킷을 거의 독점한다. 스캐너 가동 중엔 위 모든 예산이 무의미해지므로, **스캐너와 상시 감시를 동시에 돌리지 말거나** 스캐너에 별도 저우선 슬라이스를 두는 게 맞다(현 구조엔 우선순위 없음).

**요약 판정**: 사용자가 옳은 부분 = 관심종목 반응성은 실제로 나쁘다(가격이 얼어있음) → **워치 리프레시 루프 신설 + 동적 TTL**로 해결(API-bound, 예산 내 가능). 신중할 부분 = **P3·5분 재평가 "주기 단축"은 반응성을 안 올리고 churn·LLM비용만 올린다** → 정답은 **주기가 아니라 가격변동 임계치(3%→2%)를 낮추고, 5분 체크는 60초로 내리되(무비용) 실제 게이트는 토론 스로틀에 맡기는 것.** 전체를 관통하는 단일 원칙: **감시 주기는 `(N+W)`에 연동된 동적 값, 지속 부하는 천장 1.43의 70%(≈1.0 req/s) 이내.**

주요 파일: `backend/services/kiwoom/rate_limiter.py:40,64-88` (0.7s 실캡), `cache.py:69-78` (TTL), `backend/services/trading/risk_monitor.py:213-234` (1s 루프), `backend/services/agent_chat/position_manager.py:213,255-283` (30s 루프 + P3 60분/3%), `backend/services/agent_chat/coordinator.py:243-285` (5분 체크, 무API), `backend/services/trading/coordinator.py:194,429,1175-1205` (워치 가격이 start/승인에만 갱신 — 반응성 구멍), `frontend/src/api/client.ts:146` + `OperationsPanel.tsx` (FE 5s 폴, 최대 절감처).
